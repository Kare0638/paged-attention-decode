# Paged Attention Decode Kernel — Highlights

A decode-phase paged-attention kernel for LLM inference, implemented from scratch through 8 progressively optimized versions in **two languages** (Triton and CUDA C++), with every optimization claim backed by Nsight Compute (NCU) profiling data — and every negative result reported as plainly as the wins. Cross-validated on both a consumer GPU and a rented A100.

## 3-Minute Highlights

- **8 kernel versions, 2 languages, one problem.** Triton v1→v4 and CUDA C++ v1→v4, each version motivated by a specific NCU finding from the previous one — not a checklist of "standard optimizations," a real measure→diagnose→fix loop.
- **Split-K (CUDA v4) is the single largest win in the project: 20.64x vs. its predecessor at batch=1** — and this exact number reproduced on a rented A100 too, evidence the win is mechanistic, not a fluke of one GPU.
- **310 correctness tests**, including a 2000-case fuzz test against an independently-written reference oracle, bit-exact/near-bit-exact equivalence checks between kernel versions, and split-invariance checks for both split-K implementations.
- **Two real negative results, reported not hidden**: CUDA v2's batched shared-memory reduction cut instruction count 21% and shared-memory traffic 61% — and made zero measurable difference to latency (the kernel was bound by dependency-chain length, not instruction count). Triton v3's `num_stages` tuning was within noise at 6 of 7 batch sizes.
- **Roofline analysis uses measured, not nominal, peak bandwidth/compute** — actual on-device numbers (~314 GB/s / ~26 TFLOPS on the laptop, ~1699 GB/s / ~246 TFLOPS on the A100), not spec-sheet figures, re-measured independently on each GPU rather than assumed to carry over.
- **Compared against FlashInfer**, a production kernel library, on both GPUs — honestly loses (expected, comparing a from-scratch project to a heavily-engineered library), but the relative gap to the Triton line is consistently far smaller (1.16x–2.21x across both GPUs) than to the CUDA line (5.24x–17.23x), a real, mechanistically-grounded finding about where compiler-optimized codegen still beats hand-written CUDA.
- **Cross-hardware validation on a rented A100 caught two real bugs** a single-GPU dev loop never would have: a pytest version bump that silently broke a test's skip logic, and a hardcoded GPU name in a chart title. Both root-caused and fixed, not patched around.
- **A `num_splits` re-sweep on A100 found genuinely different behavior per kernel**: the CUDA line's tuned value transferred perfectly (still optimal), the Triton line's entire tuning axis flattened into noise on the bigger GPU — a real, non-obvious hardware-dependence finding, not assumed to generalize.

## One-Page Summary

**The problem.** Decode-phase attention is memory-bandwidth-bound: at this project's target shape (Qwen2.5-1.5B-style, GQA ratio 6, head_dim 128), arithmetic intensity is ~6 FLOP/byte, far below either GPU's measured ridge point (~84 on the RTX 3060 Laptop, ~145 on A100). On low-SM GPUs, the naive `(batch, kv_head)` grid leaves most SMs idle at real serving batch sizes — 2 thread blocks total at batch=1 on a ~28-SM laptop GPU. This project builds and profiles a paged-KV-cache decode kernel from scratch to fix that, in both Triton and CUDA C++, treating every optimization step as a hypothesis to measure, not assume.

**What was built.** Four versions each in Triton and CUDA C++ — naive baseline, a per-language structural optimization (wider tiles / batched shared-memory reduction), a second structural change (num_stages tuning / warp-shuffle reduction), and split-K (FlashDecoding-style parallelism along the sequence dimension) — plus a from-scratch fp32 reference oracle, a full correctness test suite, and an adapter comparing against FlashInfer.

**Results, both directions.** Triton's line shows a real win-then-crossover shape from wider tiles (BLOCK_N) and split-K: faster at low batch, slower at high batch, reported honestly rather than cherry-picked. CUDA's line shows a genuine null result (shared-memory batching, CUDA v2) followed by a real, mechanistically-understood win (warp-shuffle reduction, CUDA v3, from a shorter dependency chain — not higher occupancy, which actually dropped) and then the project's biggest single result (split-K, CUDA v4: 20.64x at batch=1). Every latency number is backed by an NCU explanation — occupancy limits, DRAM throughput, stall reasons, instruction counts — not asserted from wall-clock time alone.

**Engineering discipline.** Median-of-interleaved-trials benchmarking (a single best-of-N reading was found to be dominated by GPU clock-state noise, not real differences). Tolerances set from measured diffs, not guessed. A real environment hazard (installing an external library silently upgraded pinned `torch`/`triton`) caught and reverted before it could corrupt results, rather than discovered after the fact. A pre-existing dependency-resolution bug in the project's own `requirements.txt` — never caught because the working dev environment had never been rebuilt from scratch — found and fixed only because A100 validation forced a genuinely clean install.

**Honest limitations, stated rather than hidden.** CUDA still trails Triton by roughly an order of magnitude in absolute terms (though the relative gap has closed sharply across four versions: ~44x at v1, ~2.8x at v4). NCU profiling on the rented A100 is structurally blocked by the cloud provider's container security model — confirmed via direct testing, not assumed, and documented as a real, provider-level dead end rather than silently dropped from scope. Shipped `num_splits` defaults are still the laptop-tuned values, not made GPU-adaptive at runtime — checked, not blindly assumed, to still be reasonable on A100 (see above), but a deliberate scope boundary against building a fully auto-tuning system.
